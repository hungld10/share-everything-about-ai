Từ Demo Thành Production — Một Câu Chuyện Thực

Năm 2024, một startup AI healthcare demo thành công trên môi trường nội bộ. Cuộc demo hoàn hảo: Voice receptionist trả lời trong 280ms, giọng tự nhiên, context-aware.

Ba tuần sau, họ deploy lên production qua Twilio — kết nối điện thoại thực tế.

Đội engineering đổ lỗi cho model. GPT-4o chưa đủ tốt? Prompt sai? Cần fine-tune?

Sai. Model là 20% của problem. 80% là kiến trúc — cụ thể: demo dùng HTTP POST requests để gửi audio. Production không chịu được. Đây là lý do bạn cần hiểu WebSocket.

Tại sao HTTP không phù hợp cho Voice AI?

HTTP hoạt động theo mô hình request-response: Client gửi request → Server xử lý → Server trả response → Kết nối đóng.

Vấn đề cơ bản

Cuộc hội thoại voice là liên tục và hai chiều đồng thời. Khi nói chuyện với AI:

  • Cả hai bên có thể "nói" bất cứ lúc nào
  • Audio là dòng dữ liệu liên tục — cứ mỗi 20ms lại có chunk mới
  • Cần truyền 50 chunks mỗi giây, hai chiều cùng lúc
HTTP Request-Response
Header overhead 200-500 bytes
Mỗi chunk 20ms cần 1 request mới
50 chunks/giây = 50 requests/giây
Server push? ❌ Không thể
Total overhead 50-150% 😱
WebSocket
Frame overhead 2-14 bytes
50 chunks/giây = 50 frames (1 conn)
Connection Persistent (1 lần mở)
Server push? ✅ Bất cứ lúc nào

Với latency budget chỉ 300ms: Overhead 50-150% của HTTP sẽ lấy mất hàng trăm millisecond. WebSocket <5% overhead cho phép dùng hết budget cho AI xử lý.

Những nỗ lực "hack" HTTP để realtime

Trước khi WebSocket ra đời (2011), developer cố gắng tạo realtime trên HTTP bằng các kỹ thuật:

🔁

Polling

Client gửi request liên tục (mỗi 100ms) để hỏi "có dữ liệu mới không?". Đa số request rỗng. Tốn băng thông, không nhanh.

⏳

Long Polling

Server giữ connection mở cho đến khi có dữ liệu. Nhưng vẫn một chiều và có khoảng "chết" giữa responses.

📡

Server-Sent Events (SSE)

Server push liên tục xuống client. Nhưng chỉ một chiều. Client gửi ngược lại phải mở request riêng.

Tất cả là "hack" — cố ép giao thức một chiều thành hai chiều. Voice AI cần giải pháp thiết kế từ đầu.

WebSocket — Giải pháp được thiết kế cho realtime

WebSocket (RFC 6455, 2011) là giao thức truyền thông hai chiều, full-duplex, persistent trên một TCP connection duy nhất.

Cả client và server có thể gửi dữ liệu bất cứ lúc nào mà không cần request/response cycle.

Cách hoạt động

  1. Opening Handshake — HTTP Upgrade request với header `Upgrade: websocket`
  2. Server đồng ý — Response 101 (Switching Protocols)
  3. Connection thiết lập — Connection TCP không còn nói HTTP
  4. Streaming — Cả hai bên gửi frames liên tục suốt cuộc gọi

Frame Structure

Mỗi WebSocket frame có header tối thiểu 2-14 bytes (so với hàng trăm bytes HTTP header).

So sánh: Audio chunk 20ms (G.711 8kHz = 320 bytes)

HTTP:

~300B header + 320B payload = 50% overhead 😱

WebSocket:

~2B header + 320B payload = <1% overhead 🚀

Đặc điểm WebSocket quan trọng cho Voice AI

🔄

Full-duplex

Hai chiều đồng thời trên 1 connection. User nói (gửi) lúc AI cũng nói (nhận) — nền tảng của barge-in.

⚡

Overhead cực thấp

2-14 bytes header vs 200-500 bytes HTTP. Với audio 320 bytes, overhead chỉ <5%.

🔌

Persistent Connection

1 TCP connection suốt cuộc gọi. Tiết kiệm TCP + TLS handshake (2-3 RTT) mỗi lần.

⚔️

Server Push

Server gửi dữ liệu chủ động bất cứ lúc nào. Client không phải hỏi.

⏱️

Latency tối thiểu

Không request/response cycle. Dữ liệu gửi gần như tức thì.

💪

Handshake một lần

HTTP Upgrade + TLS tốn 50-150ms. Nhưng chỉ một lần duy nhất cho cả cuộc gọi.

Hai pattern WebSocket trong Voice AI

Pattern 1: Browser Direct WebSocket

Luồng: Browser ↔ AI trực tiếp
Browser —token→ Server
(auth only) —token→ Browser ════WSS════ AI Model
Đặc điểm:
  • Server chỉ làm authentication (cấp ephemeral token)
  • Audio đi thẳng browser ↔ AI, server không chạm
  • Latency tối thiểu vì không qua server

Pattern 2: Phone Double WebSocket qua Server

Luồng: Phone → Server → AI (transcode)
Phone/PSTN → Twilio ═WS#1═ Server
(transcode) ═WS#2═ AI Model
Đặc điểm:
  • WSS #1: Twilio stream G.711 (8kHz) → Server
  • WSS #2: Server stream PCM 16kHz → AI Model
  • Server ở giữa transcode: G.711 → PCM → upsample
  • Server quản lý session state (ID, transcript)
Lý do Double WebSocket: Twilio gửi audio qua WS#1, server xử lý/transcode, rồi forward qua WS#2 đến AI. Hai WebSocket này phải giao tiếp qua shared memory của 1 process — đây là lý do Unified Server pattern (chủ đề 12) quan trọng.

Failure Scenarios — Recovery patterns
1. Network Disconnect: Packet loss detected → Backoff 1s → Exponential backoff (1s, 2s, 4s...) → Reconnect
2. AI Crash: Model error → Server sends close code 1011 (Server Error) → Client recognizes 1011 → Auto-reconnect
3. Ping/Pong Timeout: Server waits for pong → No pong after 30s → Assume connection dead → Close & Reconnect
4. Server Restart: SIGTERM → Graceful drain (30s) → Send close code 1001 (Going Away) to all connections → Load balancer routes to new server

Connection Lifecycle

1. Opening Handshake

HTTP Upgrade request → 101 response. Mất 1 RTT (~20-50ms). Nếu WSS, thêm TLS handshake. Tổng: 50-150ms (một lần duy nhất).

2. Active Communication

Frames truyền hai chiều liên tục. Kéo dài suốt cuộc gọi (hàng phút). Cả hai bên gửi data frames (audio) và ping/pong frames (keep-alive).

3. Ping/Pong (Heartbeat)

Server gửi ping frame định kỳ (15-30 giây), client phải trả pong. Nếu không nhận pong → client đã disconnect → cleanup resources (audio buffer, session state). Quan trọng: Nếu không phát hiện, resources leak.

4. Closing Handshake

Một bên gửi close frame, bên kia acknowledge. Status code cho biết lý do: 1000 (normal), 1001 (user tắt browser), 1006 (abnormal). Server quyết định: cuộc gọi kết thúc bình thường → analytics, disconnect bất thường → error log + retry.

WSS — WebSocket Secure

WSS (WebSocket Secure) = WebSocket trên TLS, tương tự HTTPS với HTTP.

Bắt buộc production vì:

🔒

Bảo mật dữ liệu

Audio là dữ liệu nhạy cảm (thông tin cá nhân, y tế, tài chính). TLS mã hóa toàn bộ.

🌐

Browser requirement

Browser modern block WS không mã hóa từ trang HTTPS. Voice AI chạy HTTPS → cần WSS.

📞

Twilio/Telnyx requirement

Nhà cung cấp telephony chỉ stream qua WSS, không chấp nhận WS.

⚡

Overhead nhỏ

TLS handshake: 50-100ms (một lần). Mã hóa/giải mã frame: vài microsecond — không đáng kể.

Tóm tắt — Những gì cần nhớ

HTTP không phù hợp: Overhead 50-150% khi cần 50+ chunks/giây, hai chiều đồng thời. Server không push được.
WebSocket là đáp án: Persistent, full-duplex, overhead <5%. Một connection mở suốt cuộc gọi.
Hai pattern khác nhau: Browser = Direct WS (audio thẳng browser ↔ AI). Phone = Double WS qua server (transcode).
Lifecycle quan trọng: Ping/pong phát hiện disconnect, close frame cho biết lý do, graceful shutdown tránh rơi call.
WSS bắt buộc: Browser, Twilio/Telnyx đều yêu cầu. TLS overhead không đáng kể.
