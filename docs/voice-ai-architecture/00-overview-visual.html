Tại sao đây là bài toán kiến trúc?

Phần lớn tài liệu về Voice AI tập trung vào 20% — chọn model nào, prompt thế nào, fine-tune ra sao. Nhưng 80% còn lại — system engineering — là yếu tố quyết định liệu hệ thống có sống được ngoài môi trường production.

Một startup healthcare đã demo Voice AI ấn tượng với latency 280ms. Ba tuần sau, khi launch thật, cuộc gọi đầu tiên bị: 2 giây im lặng, tiếng vỡ, AI ngắt lời user. Không phải vấn đề model — vấn đề là thiếu hiểu biết về G.711, ephemeral token, barge-in state machine, pre-connect.

5 lý do Voice AI chết ở production

Không phải vì model. Là vì kiến trúc hệ thống.

🔊

1. Audio codec không khớp

User gọi từ điện thoại → audio đến server ở G.711 8kHz. AI model cần PCM 16kHz. Nếu conversion sai → tiếng vỡ, AI nhận diện sai.

⏱️

2. Latency tích lũy

STT 280ms + LLM 420ms + TTS 180ms = 940ms. User cảm thấy "chậm" ở 400ms. Mỗi bước tưởng "chấp nhận được" nhưng cộng lại vượt ngưỡng.

💾

3. Session state mất khi disconnect

User nghe vùng sóng yếu, call drop rồi gọi lại. Nếu session không persist → AI không nhớ conversation trước, phải bắt đầu lại.

🗣️

4. Barge-in không hoạt động

AI đang đọc dài. User ngắt lời. AI tiếp tục nói đè lên user. Lỗi state machine, không phải lỗi model.

🔇

5. 2–3 giây im lặng sau khi bắt máy

Server phải kết nối AI, load system prompt, generate lời chào → mất 2–3 giây. User nghĩ cuộc gọi bị lỗi → cúp máy.

Kiến trúc tổng thể — 2 Channel, 1 Core

Hệ thống Voice AI production chia làm 4 tầng, với nguyên tắc cốt lõi: 2 channel đầu vào hoàn toàn khác nhau — hội tụ về cùng 1 AI Core.

Insight cốt lõi: Channel chỉ là adapter — Core mới là bộ não. Browser và Phone là 2 thế giới hoàn toàn khác nhau về codec, protocol, và latency profile. Phần lớn bug production nằm ở lớp adapter này.

Audio Pipeline — Nguyên tắc bất đối xứng

Thành phần mà hầu hết tutorial bỏ qua: inbound và outbound audio pipeline không phải là mirror image của nhau.

Inbound

📱 Phone → AI · Buffer được

60ms buffer nằm dưới ngưỡng perception (~80ms). Gom đủ chunk trước khi xử lý giúp model chính xác hơn. Audio từ phone (8kHz G.711) → decode → upsample → buffer → AI input (16kHz PCM).

Outbound

🔊 AI → Phone · Zero buffer

Bất kỳ delay nào ở output đều cảm nhận được ngay lập tức. Buffer output = tiếng nói bị "giật". AI output (24kHz PCM) → downsample → encode → phone output (8kHz G.711) — tất cả phải immediate.

⚠️ Lỗi phổ biến: Apply cùng buffer strategy cho cả 2 chiều. Kết quả là AI nghe "lag" dù metrics P95 vẫn ổn — vì buffer outbound không xuất hiện trong latency measurement.

Ephemeral Token — Tại sao API key không được vào browser

Với channel browser, có một vấn đề bảo mật cơ bản: WebSocket cần kết nối thẳng đến AI endpoint — nhưng không thể đặt API key trong client code vì bất kỳ ai cũng đọc được.

CONTROL PLANE

Lấy token qua HTTP server

  • Browser → Server POST /api/live-token
  • Server verify auth, lấy API key từ environment
  • Return ephemeral token (30min TTL)
  • API key LUÔN ở server, không bao giờ expose
DATA PLANE

Stream audio trực tiếp (zero server latency)

  • Browser ↔ AI Model (WebSocket direct)
  • Sử dụng ephemeral token từ control plane
  • Server không bao giờ chạm vào audio
  • Real-time, bidirectional stream

4 Kiến trúc AI Pipeline — Trade-off

Đây là quyết định kiến trúc quan trọng nhất — và không có "đúng/sai" tuyệt đối, chỉ có trade-off.

Pipeline Latency Cost/min Maturity Phù hợp
Cascaded 600ms – 1.5s $0.10–0.22 ⭐⭐⭐⭐ Healthcare, Legal, Enterprise
Speech-Native 160–400ms $0.06–0.15 ⭐⭐⭐⭐ Consumer apps (GPT-4o Realtime)

Các Pattern Kiến trúc Production

🏗️

Unified Server — Anti-microservices có chủ đích

Gom HTTP + WebSocket + audio bridge vào cùng 1 process. Audio bridge truy cập session state mỗi ~20ms — nếu tách microservices, mỗi hop tốn 1 network round-trip. In-memory: ~0.1µs. Network: ~0.5ms. Khác nhau 5.000 lần.

⚡

Speculative Tool Calling — Che latency bằng parallelism

Khi AI nhận diện intent (ví dụ: flight booking), bắt đầu gọi API trong lúc user vẫn đang nói. Khi user nói xong, API đã có kết quả. Latency bị "che" bằng user's speaking time — user không cảm thấy bất kỳ delay nào.

🔀

Barge-in State Machine — User có quyền ngắt lời

LISTENING → PROCESSING → SPEAKING. Khi VAD phát hiện user nói lại trong lúc AI đang nói: cancel TTS ngay lập tức, transition về LISTENING. Lỗi phổ biến: chờ AI nói xong rồi mới xử lý interrupt — user đã cúp máy lâu rồi.

📋

Template-Driven System

Không hardcode conversation flow trong code. Persona, prompt, flow config đều là dữ liệu trong Template Store. Thay đổi behavior của AI mà không cần deploy lại code — phù hợp khi cần nhiều AI persona cho nhiều khách hàng khác nhau.

Key Takeaways

📐

Voice AI = 20% Model + 80% Architecture

Model không quyết định tất cả. System architecture — từ audio codec, latency budget, session management đến barge-in logic — mới là yếu tố chính.

🔌

2 Channel, 1 Core

Browser (48kHz Opus) và Phone (8kHz G.711) là 2 thế giới khác nhau. Channel chỉ là adapter. Core là bộ não duy nhất.

⚖️

Bất đối xứng là quy tắc

Inbound pipeline có thể buffer (60ms), outbound phải zero-buffer. Latency được đo từ inbound, nhưng outbound delay cảm nhận được ngay.

🔐

Tách control plane & data plane

Control plane: HTTP (auth, token). Data plane: WebSocket (audio). API key LUÔN ở server, client chỉ thấy token tạm.

⏱️

Latency budget là ràng buộc

STT + LLM + TTS không phải cộng tuyến tính. Mỗi bước tưởng chấp nhận (280ms, 420ms) nhưng cộng lại vượt ngưỡng (400ms).

🎯

Pre-connect làm sớm, không phải làm nhanh

Giải quyết 2–3 giây im lặng bằng cách bắt đầu setup từ lúc phone reo, không phải từ lúc user bắt máy.
