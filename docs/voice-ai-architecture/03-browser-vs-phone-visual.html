Thế Giới 1: Browser — WebRTC, Opus, Full Quality

Codec: Opus ở 48 kHz

Browser native WebRTC mặc định dùng Opus codec — được thiết kế cho speech realtime.

📊 Sampling Rate
✓ 48 kHz (phạm vi nghe của người)
✓ Hỗ trợ 5 tần suất: 8, 12, 16, 24, 48 kHz
🎚️ Adaptive Bitrate
✓ 10 kbps → 128+ kbps (tự động điều chỉnh)
✓ TWCC: Thích ứng với tình trạng mạng
🎙️ Quality Feel
✓ MOS ~4.1-4.3 (toll-quality)
✓ Natural, nuanced, tự nhiên
🎵 Audio Bandwidth
✓ ~8,438 Hz (full speech frequencies)
✓ Breathiness, sibilants, tone color rõ ràng
⚙️ Echo Cancellation
✓ AEC3 (Google, tích hợp sẵn)
✓ Delay-agnostic, automatic
📡 Jitter Buffer
✓ NetEQ (adaptive, self-tuning)
✓ 15-120ms range, automatic
Latency: 150-250ms end-to-end (một chiều) — do UDP peer-to-peer, optimize cho real-time

Adaptive Bitrate: TWCC

Opus không fixed bitrate. WebRTC liên tục monitor mạng:

📊 TWCC (Transport-Wide Congestion Control): Receiver ước tính bandwidth khả dụng → gửi feedback về sender → sender điều chỉnh Opus bitrate (10 → 50 → 128 kbps). Kết quả: không "trơ" tiếng khi mạng yếu, không lãng phí bandwidth khi mạng tốt.

Architecture: Direct WebSocket

Browser channel không qua server processing:

Browser ═WSS═ AI Model

Audio truyền trực tiếp 48 kHz Opus → Server không chạm → latency minimal

Thế Giới 2: Phone — PSTN, G.711, Limited Quality

Codec: G.711 ở 8 kHz

Khi user gọi vào số điện thoại, Twilio stream audio = G.711 μ-law ở 8 kHz.

📊 Sampling Rate
✗ 8 kHz (thập niên 1970, PSTN legacy)
✗ Hẹp: chỉ voice frequency (300-3400 Hz)
📈 Fixed Bitrate
✗ 64 kbps (không thay đổi)
✗ Predictable nhưng không thích ứng
🎙️ Quality Feel
✓ MOS ~4.1-4.3 (toll-quality)
✗ Acceptable nhưng "tinny", không tự nhiên
🎵 Audio Bandwidth
✗ ~3,969 Hz (speech intelligibility only)
✗ Thiếu breathiness, sibilants chi tiết
🔄 Echo Cancellation
⚠️ PSTN hybrid echo (~64ms window)
⚠️ AI phải detect + suppress outbound echo
📡 Jitter Buffer
⚠️ Manual adaptive buffer (40-80ms)
⚠️ Complex tuning, tùy PSTN quality
Vì Sao 8 kHz? PSTN thiết kế từ 1950s. 8 kHz = 16 kHz Nyquist frequency = đủ cho speech intelligibility. Dù bandwidth rẻ hôm nay, PSTN vẫn "bị tóc" ở 8 kHz vì backward compatibility.

Architecture: Double WebSocket + Transcode

Phone channel phải đi qua server để xử lý:

Twilio
WS#1 → Server
Transcode → AI Model
WS#2

Audio 8kHz → Server decode G.711 → upsample → process → downsample → encode → Twilio

Latency: 150-200ms (PSTN ~100ms + gateway buffer ~50-100ms) — dù network nhanh, server processing + codec conversion thêm latency

So Sánh Trực Tiếp: Browser vs Phone

Tiêu chí Browser (WebRTC) Phone (PSTN)
Codec Opus G.711 μ-law
Sample Rate 48 kHz 8 kHz
Bitrate Adaptive 10-128+ kbps Fixed 64 kbps + overhead
Bandwidth ~8,438 Hz (full speech) ~3,969 Hz (speech only)
Quality Natural, nuanced Acceptable, but "tinny"
Network Adaptive Yes (TWCC) No (fixed)
Echo Handling AEC3 (automatic) PSTN hybrid + AI suppress
Latency 150-250ms 150-200ms
Architecture Peer-to-peer (WSS direct) Gateway + transcode (double WSS)

Preprocessing: Nơi Hai Thế Giới Gặp Nhau

Browser Path — Minimal Processing

Audio từ browser đến AI Model:

🌐 Browser → AI Model
Mic (48 kHz PCM)
↓
AEC3 + Noise Suppression (Browser)
↓
Opus Encode (adaptive bitrate)
↓
WebSocket → Server
↓
Opus Decode → 16 kHz PCM
↓
AI Model (STT + LLM + TTS)

Key point: Minimal preprocessing. Opus 48kHz → 16kHz, không cần đổi codec.

Phone Path — Heavy Processing

Audio từ phone đến AI Model:

☎️ Phone → AI Model
Twilio WebSocket (G.711 μ-law 8 kHz)
↓
G.711 Decode → PCM 8 kHz
↓
Upsample 8 kHz → 16 kHz
↓
VAD: Voice Activity Detection
↓
Barge-in: Cut TTS if user speaking
↓
AI Model (STT + LLM + TTS)
↓
Downsample 24 kHz → 8 kHz
↓
G.711 Encode → μ-law
↓
Twilio WebSocket → Phone

Key point: Heavy preprocessing. Receive 8kHz → upsample → AI → downsample → 8kHz. Mỗi resample = cơ hội tăng latency hoặc giảm chất lượng.

❓ Tại sao phải upsample 8 kHz → 16 kHz?
  • STT (Speech-to-Text): Whisper, Google STT expect 16 kHz. 8 kHz = thiếu consonant detail → WER (Word Error Rate) tăng.
  • TTS Quality: AI TTS model train ở 24 kHz. Nếu output 8 kHz, tiếng méo mó → phải upsample trước, downsample sau.

Voice Activity Detection & Barge-in

VAD — Phát Hiện Người Nói

Khi nào user đang nói vs. đang nghe TTS?

⏱️ Latency
Real-time detection: ~20-100ms (tùy algorithm)
🎯 Accuracy
~85-95% (tùy noise level)
📱 Use Case
Detect user speech → cut TTS playback (barge-in)

Barge-in — User Nói Chen Ngang

Khi user nói trong khi AI đang nói TTS:

🔊

Inbound Audio Arrives

User speech detected in G.711 8 kHz input stream

⚡

VAD Triggers

Voice activity detected → signal to stop TTS

🎤

New Input to AI

User speech forwarded to STT/LLM, new response generated

📊

Latency Budget

User speaks → VAD detects (20-50ms) → AI receives → AI cuts TTS → <600ms (natural)

Challenge: Timing — user speaks → latency → AI detects → latency → AI stops TTS. Average 200-300ms. If VAD miss user speech or latency too high, overlap happens (bad experience).

Jitter Buffer & Adaptive Playout

Problem: Network Jitter

Network doesn't deliver packets uniformly:

Expected: Packet 1 at T, Packet 2 at T+20ms, Packet 3 at T+40ms
Actual: Packet 1 at T, Packet 2 at T+45ms, Packet 3 at T+15ms
Result: Audio gập gập, không mượt ❌

Solution: Jitter Buffer

Collect packets vào buffer, phát theo regular schedule:

❌ Fixed Buffer (cũ)
Deterministic latency Pro
On heavy jitter Buffer overflow, dropouts
Use case Stable network only
✅ Adaptive Buffer (modern)
Monitor packet arrival Dynamic adjust
Handle variable jitter Minimize gaps, latency
Typical range 15-120ms

How: Monitor average arrival delay, expand buffer if delay increasing, shrink if stable. Compression/expansion (time-scaling) when packet missed.

Result: Natural playback dù network có jitter.

Tại Sao Kiến Trúc Phải Khác Nhau

Browser Channel — Direct WebSocket

Audio truyền thẳng từ browser đến AI:

Browser ═WSS═ AI Model

Ưu điểm: Audio 48 kHz direct, server không chạm → latency minimal. Client-side AEC → network không phải handle echo. Adaptive bitrate auto-adjust quality.

Phone Channel — Double WebSocket + Transcode

Audio phải đi qua server để xử lý:

Phone (8 kHz) ═WSS#1═ Server
(Transcode, VAD, Echo) ═WSS#2═ AI Model
(16 kHz in)

Tại sao: Audio format khác (8 kHz vs 16 kHz), server handle codec conversion, upsampling/downsampling, VAD, barge-in, echo suppression. Không thể bypass server.

Insight: Hai channel không thể dùng cùng architecture vì audio format và processing pipeline quá khác nhau. Đây là lý do bài 04 sẽ giải thích "Unified Server Pattern" — cách triển khai 2 WebSocket + transcode mà không kill latency.
